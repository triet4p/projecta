# v0.1 Compatibility Baseline

**Status:** DRAFT
**Sprint:** S2-04 — Freeze the v0.1 compatibility baseline
**Date:** 2026-07-28

## 1. Purpose

This document freezes the v0.1 ontology surface at the point of the Sprint 1 release. It serves as the contract that v0.2 must not break: every released IRI, every graph/query behavior, and all 32 Sprint 1 validation checks must continue to pass after v0.2 additive changes are applied.

Any v0.2 change that would break this baseline is, by definition, a MAJOR (1.0) change — not a MINOR (0.2) change — and requires a separate migration decision.

## 4. Graph and Query Behavior Contract

### 4.1. Query Surface

All 14 competency queries in `ontology/competency-questions/quick-note-queries.rq` are part of the compatibility contract. They must:

- Parse without syntax errors in Jena (`sparql --query`).
- Return the exact row counts listed in §3.4–§3.5.
- Return the correct set of `NoteItemType` values for CQ-NOTEITEM-001.
- Return count = 1 for all six types in CQ-COUNT-001.
- Return count = 1 for CQ-COUNT-002.

### 4.2. Demo Graph

The demo graph `ontology/examples/quick-note-demo.trig` must:

- Contain exactly 1 named graph.
- Contain exactly 9 instances: 1 Project, 1 Person, 1 Note, 6 NoteItems.
- Every NoteItem must have `hasItemType`, `contentText`, and a path back to its parent Note via `isItemOf`.
- The Note must have `belongsToProject`, `authoredBy`, `recordedAt`, and `name`.

### 4.3. Negative Fixture Behavior

Each negative fixture must:

- Pass `riot --validate` (be syntactically valid RDF).
- Cause its corresponding negative query to return `true` when merged with the clean ontology + demo graph.
- Not cause any Sprint 1 competency query to return incorrect results when the clean demo graph is used alone.

### 4.4. PROV-O Alignment

- `projecta:authoredBy` is a subproperty of `prov:wasAttributedTo`.
- `projecta:recordedAt` is a subproperty of `prov:generatedAtTime`.
- No custom provenance vocabulary exists — all provenance reuse goes through PROV-O.

### 4.5. Naming Convention Compliance

- Classes: PascalCase (`NoteItem`, `SourceArtifact`).
- Object and datatype properties: camelCase (`belongsToProject`, `authoredBy`, `hasNoteItem`, `contentText`, `recordedAt`).
- Controlled individuals: kebab-case (`progress-update`, `research-need`).
- The `projecta:` prefix is the sole vocabulary prefix — no module-specific prefixes exist.

## 5. v0.2 Classification: Additive or Breaking?

### 5.1. Classification

**v0.2 is classified as an ADDITIVE (MINOR) release.** Per the namespace policy ([docs/ontology/namespace-policy.md](namespace-policy.md) §5):

> MINOR (`1`→`2`): Additive changes — new classes, new properties, new shapes that don't invalidate existing data.

### 5.2. What v0.2 Must Add (Additive Changes)

| Change | Type | Justification |
|---|---|---|
| New classes: `Candidate`, `LifecycleStatus`, `AssertedFact`, etc. | Additive | New terms in the vocabulary namespace |
| New object properties: `candidateStatus`, `reviewDecision`, `supersededBy`, etc. | Additive | New properties with no overlap with v0.1 domains/ranges |
| New datatype properties: `validFrom`, `validTo`, `rejectionReason`, `generator`, etc. | Additive | New literal properties |
| New controlled individuals: lifecycle states (`extracted`, `validated`, `pending-review`, `confirmed`, `rejected`, `asserted`, `superseded`, `retracted`) | Additive | New vocabulary terms |
| New ontology modules: `provenance.ttl`, `temporal.ttl` | Additive | Co-members of the same ontology IRI, sharing the namespace |
| New named graphs: `/candidates`, `/asserted`, `/inferred`, `/provenance` per project | Additive | New graph IRIs; v0.1 graph `/sources` is untouched |
| SHACL shapes in `ontology/shapes/` | Additive | Validation shapes are new artifacts; they don't change the vocabulary |
| New competency questions and SPARQL queries | Additive | New query files; v0.1 queries continue to run against the v0.1 demo graph |
| Ontology version metadata update | Additive | New version IRI `v/0.2/` alongside existing `v/0.1/` |

### 5.3. What v0.2 Must NOT Do (Breaking Changes)

| Forbidden Change | Why It's Breaking |
|---|---|
| Rename any v0.1 IRI | Consumers referencing the old IRI break |
| Change domain or range of any v0.1 property | Existing triples may become invalid |
| Delete or repurpose any v0.1 class, property, or individual | Consumers depending on the term break |
| Change the superclass hierarchy of any v0.1 class | Inference and query patterns may produce different results |
| Change any controlled individual's IRI or `rdfs:label` | Queries filtering by IRI or label break |
| Modify the demo graph (`quick-note-demo.trig`) in a way that changes any of the 14 CQ results | The 32-check baseline fails |
| Add mandatory properties to v0.1 classes that would invalidate the existing demo graph | The demo graph would fail validation |
| Change the `owl:versionIRI` or `owl:versionInfo` of `v/0.1/` | The v0.1 release metadata must remain immutable |
| Remove or rename `projecta:` as the vocabulary prefix | All existing Turtle/SPARQL files break |
| Change the base IRI from `https://w3id.org/projecta/ontology/` | All existing IRIs break |

### 5.4. Gray Areas (Require Explicit Decision)

| Change | Risk | Recommendation |
|---|---|---|
| Adding `rdfs:subClassOf` from a v0.1 class to a new v0.2 class | Low — additive hierarchy extension | Permitted if the new superclass is purely organizational |
| Adding a new superproperty to an existing v0.1 property | Low — SPARQL queries using the property still work; new inferences are additive | Permitted; document in changelog |
| Broadening a v0.1 property domain (e.g., `authoredBy` from `SourceArtifact` to `Entity`) | Medium — may cause unexpected inference | Do NOT broaden in v0.2; if needed, create a new property and deprecate in v1.0 |
| Adding `owl:inverseOf` to an existing property that lacked one | None — inverse declarations don't change existing triples | Permitted |
| Adding `rdfs:comment` translations or fixing typos in labels | None — metadata-only changes | Permitted; PATCH-level change |

## 6. Regression Test Contract

### 6.1. Execution

```bash
docker compose run --build --rm ontology-test
```

Must exit 0 after v0.2 changes are applied. The command must:

1. Validate all v0.1 syntax files (SYN-01 through SYN-06).
2. Validate v0.2 syntax files (new files — additive).
3. Verify v0.1 vocabulary counts (VOC-01 through VOC-04) — or their updated additive equivalents.
4. Run all 14 v0.1 competency queries against the v0.1 demo graph and verify exact results.
5. Run all v0.2 competency queries against the v0.2 lifecycle demo graph.
6. Verify all negative fixture behaviors (clean → false, bad → true).
7. Run SHACL validation on positive and negative v0.2 fixtures.

### 6.2. What a Regression Failure Looks Like

If any of the following occur, the change is breaking and must be reverted or escalated to a MAJOR version decision:

- A v0.1 syntax file fails `riot --validate`.
- A v0.1 competency query returns a different row count.
- A v0.1 ASK query returns the wrong boolean.
- A negative detector returns `true` on the clean v0.1 demo graph.
- A vocabulary count check fails (fewer classes/properties/individuals than expected).
