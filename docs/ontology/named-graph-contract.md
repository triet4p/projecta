**Date:** 2026-07-28

## 1. Purpose

This document defines the canonical named-graph IRI templates, the contents and authority of each graph, the isolation rules, and the dataset contract that all Projecta data must follow. It is the authoritative reference for SHACL isolation shapes (S2-13), competency query graph scoping (S2-15), and the Docker validation harness (S2-16).

## 2. Graph IRI Templates

Every project-scoped dataset uses exactly five named graphs:

```text
https://w3id.org/projecta/data/project/{project-id}/sources/
https://w3id.org/projecta/data/project/{project-id}/candidates/
https://w3id.org/projecta/data/project/{project-id}/asserted/
https://w3id.org/projecta/data/project/{project-id}/inferred/
https://w3id.org/projecta/data/project/{project-id}/provenance/
```

`{project-id}` is a stable, URL-safe project identifier (kebab-case, e.g., `ecommerce-checkout`).

## 3. Graph Contents and Authority

### 3.1. Sources Graph

**IRI template:** `/project/{id}/sources/`

| Aspect | Rule |
|---|---|
| **Contains** | `Note` and `NoteItem` instances (v0.1 source artifacts) |
| **Authority** | The capturing human actor — the system records what was captured |
| **Immutability** | Content is immutable once captured; edits create new revisions (deferred to Sprint 3+) |
| **Typical classes** | `projecta:Note`, `projecta:NoteItem`, `projecta:Person`, `projecta:Project` |
| **Provenance properties** | `projecta:authoredBy`, `projecta:recordedAt`, `projecta:belongsToProject` |

### 3.2. Candidates Graph

**IRI template:** `/project/{id}/candidates/`

| Aspect | Rule |
|---|---|
| **Contains** | `Candidate` instances — proposed knowledge items awaiting human review |
| **Authority** | The extraction process (manual or automated) — candidates are proposals, not truth |
| **Immutability** | Candidate content is immutable once created; status changes are recorded as provenance activities |
| **Typical classes** | `projecta:Candidate` |
| **Provenance properties** | `prov:wasDerivedFrom` (→ source NoteItem), `prov:wasGeneratedBy` (→ extraction activity), `projecta:candidateStatus`, `projecta:generator`, `projecta:proposedOntologyVersion`, `prov:generatedAtTime` |

### 3.3. Asserted Graph

**IRI template:** `/project/{id}/asserted/`

| Aspect | Rule |
|---|---|
| **Contains** | Asserted knowledge — human-confirmed `KnowledgeItem` instances |
| **Authority** | The human reviewer who confirmed the candidate and the system that promoted it |
| **Immutability** | Fact content is immutable; supersession and retraction add new facts without deleting old ones |
| **Typical classes** | `projecta:KnowledgeItem`, `projecta:Requirement` |
| **Temporal properties** | `projecta:validFrom`, `projecta:validTo` |
| **Provenance properties** | `prov:wasDerivedFrom` (→ candidate), `prov:wasAttributedTo` (→ reviewer) |

### 3.4. Inferred Graph

**IRI template:** `/project/{id}/inferred/`

| Aspect | Rule |
|---|---|
| **Contains** | Facts generated by deterministic inference rules |
| **Authority** | The inference engine — inferred facts are always traceable to the asserted facts and rules that produced them |
| **Immutability** | Regenerated on each inference run; not manually editable |
| **Typical classes** | Same as asserted graph — inferred facts use the same vocabulary |
| **Status (v0.2)** | **Empty** — no deterministic rules are implemented in Sprint 2 per S2-17 scope analysis. The graph IRI is reserved and the isolation shapes verify it is never confused with asserted |

### 3.5. Provenance Graph

**IRI template:** `/project/{id}/provenance/`

| Aspect | Rule |
|---|---|
| **Contains** | `prov:Activity` instances recording every lifecycle transition, plus `rdf:Statement` instances carrying assertion-level metadata |
| **Authority** | The system — provenance activities are recorded automatically on every state transition |
| **Immutability** | All provenance records are append-only and immutable |
| **Typical classes** | `prov:Activity`, `rdf:Statement` |
| **Key properties** | `prov:wasAssociatedWith` (→ actor), `prov:endedAtTime`, `prov:used` (→ input), `prov:generated` (→ output), `projecta:reviewDecision`, `projecta:rejectionReason` |

## 4. Graph Isolation Rules

### 4.1. Class-Based Isolation

| Class | Allowed in | Forbidden in |
|---|---|---|
| `projecta:Note`, `projecta:NoteItem` | `sources` | `candidates`, `asserted`, `inferred`, `provenance` |
| `projecta:Candidate` | `candidates` | `sources`, `asserted`, `inferred` |
| `projecta:KnowledgeItem` and subclasses | `asserted`, `inferred` | `sources`, `candidates` |
| `prov:Activity` | `provenance` | `sources`, `candidates`, `asserted`, `inferred` |
| `rdf:Statement` | `provenance` | `asserted`, `inferred` |
| `projecta:Project`, `projecta:Person` | Any graph (reference entities, not knowledge entities) | — |

### 4.2. Cross-Graph References

Cross-graph references are **required** for provenance chains. The following patterns are valid:

```text
Candidate (in /candidates)
  → prov:wasDerivedFrom → NoteItem (in /sources)           ✅ valid

KnowledgeItem (in /asserted)
  → prov:wasDerivedFrom → Candidate (in /candidates)       ✅ valid

prov:Activity (in /provenance)
  → prov:used → Candidate (in /candidates)                 ✅ valid
  → prov:generated → KnowledgeItem (in /asserted)           ✅ valid

rdf:Statement (in /provenance)
  → rdf:subject → KnowledgeItem (in /asserted)              ✅ valid
```

### 4.3. Forbidden Patterns (Detected by Isolation Shapes — S2-13)

```text
Candidate in /asserted                                    ❌ masquerading
KnowledgeItem in /candidates                              ❌ not yet confirmed
prov:Activity in /asserted                                ❌ provenance in fact graph
rdf:Statement in /asserted                                ❌ metadata in fact graph
```

## 5. Dataset Contract

### 5.1. Per-Project Completeness

A dataset for project `{id}` is complete when all five graphs exist (even if some are empty). The empty graph IRI must still be declared in the TriG file so queries scoped to that graph return empty results rather than errors.

### 5.2. Cross-Project Isolation

Entities in project A's graphs must not reference entities in project B's graphs via `prov:wasDerivedFrom`, `supersededBy`, or `belongsToProject` (which must point to exactly one project). Cross-project references without explicit authorization are detected by scope shapes (S2-13).

### 5.3. Fixture Naming Convention

```
ontology/examples/{use-case}-demo.trig        # positive fixture (complete, valid)
ontology/examples/negative-{violation}.trig   # intended-invalid fixture
```

## 6. Lifecycle Demo Fixture

The canonical lifecycle demo fixture is at:

```
ontology/examples/lifecycle-demo.trig
```

It extends the Sprint 1 `quick-note-demo.trig` scenario (project "Ecommerce Checkout Redesign", BrSE Le, sprint review note) with:

| Graph | Contents |
|---|---|
| `sources` | 1 Project, 1 Person, 1 Note, 6 NoteItems (copied from quick-note-demo.trig) |
| `candidates` | 1 Candidate extracted from the address-confirmation Requirement NoteItem |
| `asserted` | 1 Requirement promoted from the confirmed Candidate |
| `inferred` | Empty (reserved for Sprint 3+) |
| `provenance` | 3 Activities (extraction, review, assertion) + 1 `rdf:Statement` (validFrom metadata) |

### 6.1. Properties Exercised

The demo exercises all 21 new v0.2 terms:

- **Classes:** `Candidate`, `LifecycleStatus`, `KnowledgeItem`, `Requirement`
- **Object properties:** `candidateStatus`, `reviewDecision`, `supersededBy` (reserved, not exercised by single-assertion demo)
- **Datatype properties:** `validFrom`, `generator`, `proposedOntologyVersion`, `rejectionReason` (reserved), `retractionReason` (reserved)
- **LifecycleStatus individuals:** `extracted`, `confirmed`, `asserted`
- **External:** `prov:Activity`, `prov:wasDerivedFrom`, `prov:wasGeneratedBy`, `prov:wasAssociatedWith`, `prov:used`, `prov:generated`, `prov:generatedAtTime`, `prov:endedAtTime`, `rdf:Statement`, `rdf:subject`, `rdf:predicate`, `rdf:object`
