## Public and operational boundaries to preserve

### Application API and browser

- The browser calls the typed Application API over the same-origin web
  boundary; it does not call Semantic Core or Fuseki directly.
- Existing public projections use opaque project, installation, run, graph,
  and knowledge handles where the released contract requires them.
- Public failures use the bounded `application/problem+json` contract with
  safe codes and correlation IDs; storage paths, SQL, RDF internals,
  credentials, and provider payloads do not cross the boundary.
- The current local/experience context is a server-owned deterministic adapter,
  not production authentication. Production mode fails closed when it is
  selected without a reviewed provider boundary.

### Connector contract

The released connector contract is `connector-contract.v1`:

- finite descriptor and capability vocabulary;
- inbound bounded pull, resource fetch, optional non-authoritative identity
  hint, and cancellation;
- one outer deadline and no adapter/SDK/proxy/scheduler retries;
- opaque cursor proposal committed only after evidence and Semantic Core work;
- finite terminal outcomes and safe error mapping;
- connector operational state in PostgreSQL, raw bounded bytes in evidence
  storage, and semantic lifecycle through the existing Application API and
  Semantic Core boundary.

The JSON/Mock adapter remains the deterministic reference implementation.
Teams must be additive and provider-specific only inside its adapter.

### Data and isolation

- PostgreSQL owns installation, inbox/event identity, cursor, run, retry
  lineage, dead-letter, audit index, and safe read projections.
- Evidence storage owns immutable/content-addressed source bytes.
- Fuseki/TDB2 owns source, candidate, asserted, inferred, and provenance
  graphs.
- Connector operational rows, session rows, provider tokens, cursors, and
  secret metadata do not become RDF facts.
- Project predicates and safe not-found/forbidden mappings preserve
  cross-project non-existence.

## Compatibility rules for Sprint 11

1. Existing typed routes, response codes, connector lifecycle, migrations,
   replay behavior, evidence rules, semantic lifecycle, and browser journeys
   remain passing or change only through an explicitly versioned additive
   contract.
2. The new identity and secret boundaries may replace the local/test adapter
   only in the reviewed production composition; deterministic local/test
   paths remain explicit and isolated.
3. Teams configuration, tenant/team/channel identifiers, provider tokens, and
   provider payloads remain internal implementation data and must not expand
   released public DTOs.
4. No ontology version change is assumed. Any exception requires a separate
   governed proposal and human semantic approval.
