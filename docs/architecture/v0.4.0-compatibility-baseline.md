## Released projection invariants

Sprint 10 must preserve these v0.4.0 projection properties:

- Project selection is server-owned and revalidated for each operation.
- Public identifiers are opaque handles, normally revision-bound.
- Graph output is a finite domain projection, never an RDF/SPARQL browser.
- Graph node and edge types are allowlisted display values.
- Candidate, source, asserted, inferred, provenance, lifecycle, and freshness
  states remain distinct rather than collapsed into one status.
- Graph and companion table views use the same bounded projection.
- Notes preserve source text, typed NoteItems, evidence offsets, provenance,
  and candidate linkage.
- Candidate review is separate from assertion; confirmation is an explicit
  lifecycle operation.
- Project scope, actor context, request correlation, and safe problem mapping
  are enforced by the Application API boundary.
- Replay/idempotency behavior for released capture workflows returns the
  original committed representation and does not create a partial semantic
  write.

## Compose baseline

The v0.4.0 topology is Docker Compose based. The base file contains these
services:

- `fuseki` and `fuseki-bootstrap` for RDF persistence/bootstrap.
- `semantic-core` for the Java semantic boundary.
- `api` for the Python Application API.
- `web` for the static SPA, enabled by the `web` profile.
- `jena`, `ontology-test`, and system-test services for tool/test profiles.

The released named profiles are:

| Profile | Purpose |
| --- | --- |
| none/default | Fuseki, Fuseki bootstrap, Semantic Core, and API vertical slice |
| `tools` | Jena and ontology test utilities |
| `web` | Static web application |
| `system-test` | Runtime and integration test services |

The baseline uses the `projecta-api-operational` named volume and the existing
local operational database path `/var/lib/projecta/operational.db`. PostgreSQL
connector state is therefore a Sprint 10 addition, not an existing v0.4.0
compatibility surface. S10-11 onward must introduce it only after G1 approval
and must preserve existing semantic state and browser journeys.

The baseline also preserves the existing Fuseki/TDB2 single-writer topology,
named volumes, health/readiness checks, non-public default API exposure, and
production image overrides. Sprint 10 must not add a broker, Kubernetes, Redis,
or a search cluster without a separate measured architecture decision.

## Release workflow baseline

The v0.4.0 tag workflow has these required jobs:

`release-contract` → `api`, `web`, `semantic-core`, `repository-contracts`, and
`system` → `publish`.

The workflow is tag-only and validates exact SemVer-shaped tags before
publication. Sprint 10 must extend this workflow with its validation, connector
system acceptance, recovery, security, and frontend format gates without
`continue-on-error` or a release bypass.

## Compatibility constraints for S10-02 onward

- Additive routes must remain typed, finite, project-scoped, and opaque.
- Connector operational state belongs in PostgreSQL/read projections, not RDF.
- Raw connector payloads belong in bounded evidence storage, not public DTOs.
- Imported source content must reuse the existing Note/NoteItem and candidate
  lifecycle; it must not become direct asserted knowledge.
- Existing v0.4.0 routes and projections must keep their response semantics,
  error boundary, correlation behavior, and lifecycle separation.
- Any required ontology vocabulary change is outside this frozen baseline and
  requires the separate ontology governance workflow plus explicit approval.
