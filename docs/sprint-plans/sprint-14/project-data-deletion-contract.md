## 1. Approved user operation (not current product capability)

1. On the Projects screen, next to each project row (not inside the in-workspace navigation), show an explicit destructive action, e.g. **Delete project**. The action MUST be discoverable per project without requiring the user to type an opaque ID.

2. Selecting it opens an explicit confirmation that states, at minimum:

   - the exact project display name and canonical `projectId` (typed re-entry of the display name or project ID is required; a single OK click is not sufficient);
   - the irreversible full-purge scope (semantic graphs, evidence objects, drafts/history, connector state, receipts, configuration audit, import-ledger entries for the scope per §3–§4);
   - what is explicitly **not** deleted (other projects, installation secrets/config, exported `.projecta` files, whole-installation backups, see §3);
   - that ALL project history for the scope is permanently removed, including review/correction/cost receipts and configuration audit rows — there is no retained history and no undo — never silent disappearance;
   - that active exports/imports must be idle and that the operation cannot be undone.

3. The server MUST re-authorize the actor, re-validate the typed identity, re-check the destination registry, and re-verify quiescence before applying. A browser confirmation alone MUST NOT delete anything.

4. The outcome MUST be truthful and finite: `deleted`, `cancelled`, `refused-<reason>` (unauthorized, unknown project, busy, recovery-required, legal-hold, space insufficient), never a silent partial state. Cancellation or refusal leaves all state unchanged.

## 4. Append-only history: exact constraint and approved exception

### 4.1 Exact blocking constraints (observed)

- PostgreSQL `apps/api/alembic/versions/0011_review_receipts_append_only.py`: `CREATE TRIGGER review_decision_receipts_append_only BEFORE UPDATE OR DELETE ON review_decision_receipts FOR EACH ROW EXECUTE FUNCTION reject_review_decision_receipt_mutation()` — the function unconditionally `RAISE EXCEPTION 'review_decision_receipts is append-only'`.
- PostgreSQL `apps/api/alembic/versions/0010_correction_burden_events.py`: identical pattern for `correction_burden_events` (`reject_correction_burden_event_mutation()`).
- SQLite `apps/api/src/projecta_api/configuration/storage.py`: `authoring_cost_events_append_only_update` (`BEFORE UPDATE`) and `authoring_cost_events_append_only_delete` (`BEFORE DELETE`) both `SELECT RAISE(ABORT, 'authoring_cost_events is append-only')`.
- The portable contract (§7.2) already records the consequence: import keeps staged receipt rows uncommitted until a complete commit can be proved, precisely because committed receipts cannot be updated/rolled back through the receipt API.

An ordinary `DELETE FROM review_decision_receipts WHERE project_id = ?` (or the correction/authoring equivalents) therefore fails closed today. Silently disabling or dropping those triggers inside a delete implementation is forbidden; only the approved exception in §4.2 below may remove in-scope project rows, and only through a reviewed migration.

### 4.2 Approved selection: full project purge under a controlled native-only exception (selected)

The owner approved **hard-delete of the project including its history under an explicit native-ownership exception** (`'Xóa hẳn, cho phép import lại'`). The A1 retain-labelled-history + registry-tombstone recommendation is superseded and MUST NOT be implemented.

- Purge scope: `review_decision_receipts`, `correction_burden_events` (PostgreSQL, by `project_id = ?`), and `authoring_cost_events` (SQLite, by `project_digest = ?`) rows for the deleted `projectId`, exactly as §3 says. No registry tombstone is recorded — the project identity is fully released so the same ID reimports as a fresh `add-project` (§7).
- Exception shape (S14-15 MUST implement exactly this, via a reviewed migration — design names below are proposed, not existing):
  - native-only: the purge path runs only inside the trusted native launcher/API boundary for the explicitly confirmed `projectId`; it is never reachable from browser-supplied SQL, connector input, or import payload handling;
  - single-project-scoped: the migration asserts the exact `projectId`/`project_digest` predicate and refuses when the predicate is missing, empty, or matches more than the confirmed scope (fail closed);
  - trigger-aware, not trigger-disabling: the reviewed migration performs the scoped delete through a constrained helper (e.g. a `SECURITY DEFINER` function or a migration-owned transaction that validates scope before touching guarded rows), then leaves the triggers in place and verifying;
  - ordinary protections unchanged: after the migration, normal `UPDATE`/`DELETE` on all three tables still raises/aborts exactly as before. No session flag, no `SET session_replication_role`, no global trigger drop/disable, and no code path that bypasses the triggers outside the reviewed migration.
- Preconditions: full pre-delete backup of the affected stores (whole-installation `BackupManager` snapshot covers data + registry + secrets), plus exact old/new verification (per-store pre/post counts: zero rows remain for the scope; every other `projectId` byte-identical).
- Consequences (stated truthfully in the confirmation and result): storage fully reclaimed; history becomes unverifiable (receipt digests/sequences/chains for that project disappear); audit semantics change and this section is the recorded approved exception to the append-only policy; rollback after catalog publication is impossible.
- Unknown legal holds fail closed: no `legal_hold`/`legalHold` concept exists anywhere in current source (verified by repo-wide search returning zero matches — there is no hold column, table, or predicate to check). If a future hold concept is ever introduced, delete MUST refuse with `refused-legal-hold` when the scope carries an unrecognized hold marker instead of bypassing it. Explicit owner confirmation overrides only `retain_until` retention hints (see §3 evidence row), never holds.

Rejected: "delete the rows but keep the triggers untouched by temporarily disabling them in code without a reviewed migration" — that is this exception without the approval and audit trail, and it MUST NOT be implemented.

## 5. Operation boundaries (approved)

- **Quiescence:** deletion MUST acquire the same kind of no-writer epoch the export/import paths use: the one native launcher instance lock, `ProjectWriteFence.maintenance_epoch`-style drain of API readers/writers (see `apps/api/src/projecta_api/export_fence.py`), and refusal with finite `DELETE_BUSY` while any export collection, import staging/publication, or `IMPORT_RECOVERY_REQUIRED` state is active. Active connector runs/attempts or `pending` suggestion workflows for the target project also refuse with `DELETE_BUSY`; the operation MUST NOT cancel or resume them.
- **Staging and journal:** deletion MUST write a destination-owned delete journal (new file, e.g. `data/deletion/journal.json`, not the import journal) with `projectId`, `projectName`, `actorId`, old catalog revision, per-store expected counts, and a finite phase (`prepared/graphs-cleared/evidence-cleared/sqlite-cleared/postgres-cleared/registry-published`). Before catalog publication any error rolls back to the pre-delete snapshot; after interruption, startup MUST detect the unfinished journal before serving and resolve to exactly the old state or exactly the new state — never a mixed state where the catalog says deleted but store rows remain (or vice versa). The journal and any staged snapshot are bounded recovery state: they are removed by bounded cleanup after the terminal commit and are NOT a persistent project-history store.
- **Space and safety:** pre-flight MUST verify staging/rollback space (same pattern as `_check_import_staging_space`), reparse-point/symlink guards on every tree walk (same as evidence/launcher guards), and same-volume atomic registry publication (`os.replace`-style + fsync + readback).
- **Other-project preservation proof:** pre/post counts per §3 (graph triple counts per role, `list_project`, SQLite five-table + digest check, `_postgres_project_count` table set) for every surviving project MUST match exactly.

## 6. Catalog, selection, and first-run behavior (approved)

- The registry file (`config/local-runtime.json`) is published last. The deleted `projectId` is removed from `projects[]` with no tombstone marker — the identity is fully released.
- Any `project_selections` row targeting the deleted project is cleared (`clear(actor)`); the API's stale-`catalog_revision` path already fails closed, and the UI MUST return to the Projects chooser with no implicit re-selection. The deleted project MUST NOT remain selectable after success or after restart.
- **Last-project rule (approved):** deleting the last remaining project leaves a persisted empty catalog (`projects: []`) that survives launcher restart and bootstrap — `provision_first_run_workspace` refuses to overwrite an existing file (`LOCAL_PROJECT_CONFIGURATION_INVALID` on `path.exists()`), so no seed placeholder is resurrected behind the user. Core/ports/shared services stay operable so a fresh project can be created afterwards. The pristine first-run placeholder (`my-projecta-workspace`) deletes like any other project; a later same-ID import is then `add-project`, not `adopt-placeholder`.

## 7. Import ledger and reimport semantics (approved)

- On delete, remove that project's ledger entries from `data/imports/ledger.json` (ledger shape `{formatVersion: 1, imports: {exportId: archiveSha256}}`; entries are keyed by `exportId`, so S14-15 MUST resolve this project's `exportId`s from the archived packages' manifests and delete exactly those keys — never the whole file). Consequence: afterwards the same archive reimports as a fresh `add-project` (ledger miss + all `_check_local_empty` predicates clear + `destinationState == "absent"`), not `IMPORT_CONFLICT`.
- The delete result MUST state how many ledger entries were forgotten for the scope, and the ledger file itself MUST never be hand-edited outside the delete transaction.
- This intentionally forgets replay protection for those `exportId`s: reimporting the exact same bytes is a new import. That is the owner-approved meaning of `'Xóa hẳn, cho phép import lại'`.

## 8. What deletion explicitly does not do

- No whole-installation reset: `config/installation.json`, `secrets/launcher.dpapi`, `.env`/master keys/passwords, `data/state/*`, `logs/`, `backups/`, `recovery/` (except the delete's own journal trees), and all non-target projects stay intact.
- No export-file or backup-copy cleanup: `exports/*.projecta`, user downloads, Drive copies, and `backups/<id>` remain; the confirmation screen MUST say so.
- No merge, overwrite, ID remap, workspace reset, or generic retention/purge-queue/retry/telemetry feature.
- No ontology term, SHACL shape, inference-rule, or materialization-lock change. No tombstone term exists or is needed — the purge releases the identity entirely, so no `skill://projecta-evolve-ontology` human-review packet is triggered by this contract. If a future design ever needs one, it follows that skill and gate.
- No production OIDC/session/membership transplantation: `projecta_oidc_login_attempts`/`projecta_sessions` are global and untouched; `projecta_project_memberships` rows for the deleted `projectId` are removed as authorization cleanup (they grant access, they are not history), and this removal is stated in the result — it is not a history purge.
- Purge limitations (truthful): logical data removal is specified here; secure disk erasure is NOT claimed. Deleted bytes may persist in whole-installation backups (`backups/<id>`), user-kept export files, filesystem free space, database WAL/freelist pages, and logs until those layers rotate. The confirmation MUST state that backups/export copies remain and that this operation is logical removal, not certified media sanitization.
